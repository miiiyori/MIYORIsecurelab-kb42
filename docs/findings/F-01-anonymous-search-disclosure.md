# F-01. Анонімний пошук віддає всі інциденти

**Статус:** Fixed  
**Що під загрозою:** поля `title` і `description` усіх інцидентів у базі  
**Компонент:** `GET /api/incidents/search` (`Scaffolding/Lab02Endpoints.cs`)  
**Пріоритет:** P1

## Умови перевірки

Перевірку починала на гілці `lab/6-hardening-review` від тегу `v0.5.0` (`09667b6`). Локальна БД у Docker після `--reset-database`, профіль `Development`, тестові облікові записи (`alice`, `bob`, `morgan`, `admin`). Інші маршрути та навантаження тут не розглядалися.

## Відтворення до виправлення

На стані `v0.5.0`:

1. Скинула базу (`--reset-database`) і запустила API у `Development`.
2. Без авторизації (без cookie) надіслала `curl.exe -i http://localhost:5080/api/incidents/search` у PowerShell (порожній параметр `q` формує шаблон `%%`, тому база повертає всі записи).
3. **Очікувано** (за матрицею доступу з ЛР 4): `401 Unauthorized` для анонімного запиту, а для `Reporter` - тільки власні інциденти.
4. **Фактично:** сервер повернув `200 OK` і список усіх інцидентів разом із `title` та `description` (зафіксовано на скріншоті `docs/evidence/lr6-f01-before.png`).

## Вплив і ймовірність

Підтверджено локальним запуском на `v0.5.0`. Будь-хто з доступом до API може без входу прочитати назви й описи чужих інцидентів. Це фактично обходить обмеження доступу з ЛР 4, бо пошук дає окремий шлях до тих самих даних. Для експлуатації не потрібні ні обліковий запис, ні роль - достатньо одного `GET`-запиту, тому ймовірність висока. У матриці ЛР 4 рядок із пошуком був позначений як такий, що не входив до того рівня, тому маршрут і лишився відкритим.

## Причина

Маршрут залишився ще з ЛР 2 без прив'язки до авторизації: на ньому немає `RequireAuthorization()`, не визначається поточний користувач і вибірка `db.Incidents` не фільтрується за `OwnerUserId`.

## Виправлення

У `Lab02Endpoints.cs` додала `RequireAuthorization()`, повернула `403 Forbidden` для `Administrator` (як і в основному списку інцидентів), а для всіх, хто не має ролі `Analyst`, додала фільтр `OwnerUserId == subject` безпосередньо в запит до БД. `Analyst` і далі бачить усі інциденти. Окремо підключила `RequireRateLimiting("search")` як додатковий контроль. Старий тест `Search_ReturnsJson` оновила під автентифікованого користувача.  
Коміт із виправленням: `3b08dd3`.

## Повторна перевірка (Retest)

Ручний запит `curl.exe -i http://localhost:5080/api/incidents/search` без cookie після виправлення повертає `401 Unauthorized` без даних інцидентів (`docs/evidence/lr6-f01-after.png`).

Автоматизовані тести: `SearchAccessTests` (`Search_Anonymous_Returns401_AndNoIncidentData`, `Search_AsReporter_FindsOwnIncident_ButNotForeignOne`, `Search_AsAnalyst_FindsForeignIncident`, `Search_AsAdministrator_Returns403`).  
Команда: `dotnet test SecureLab.sln -c Release`  
Результат (20.11.2026): **PASS** (усі 63/63 тести пройшли, включно з 4 тестами `SearchAccessTests`).

## Перевірка робочих сценаріїв

Alice знаходить власний інцидент і не бачить чужих; Morgan (`Analyst`) знаходить чужі інциденти; `SearchMechanicsTests.Search_AsAuthenticatedUser_ReturnsJson` проходить; сценарії пошуку з апострофом і контрольним вводом (S-02/T-04) працюють коректно після входу.

## Залишковий ризик

Rate limiting не замінює авторизацію - анонімний запит відхиляється раніше на етапі автентифікації. Крім того, лічильники зберігаються в пам'яті процесу (in-memory), тому між кількома екземплярами API вони не синхронізуються. Інші `GET`-маршрути поза межами цієї перевірки не тестувалися.
